# 操作流程 SOP（從接案到出稿 · 精確到每一步）

> 定位：這份是「怎麼用這個 skill 幹活」的**逐步操作手冊**。每一步寫清：**輸入 / 動作 / 命令 / 產出 / 校驗**。
> 為什麼有它：用戶 2026-09-16 —— 「策劃具體操作流程還是沒寫好，要詳細精準到每一步」。
> ⛔ **鐵律**：知識由**腳本機械注入**，不靠模型自願引用（模型只填空）。**規則寫在代碼裡，不寫在文字裡。**

---

## 總覽：一條命令鏈

```
0 收資料/門禁 ──▶ 1 組裝骨架 ──▶ 2 填空 ──▶ 3 自檢 ──▶ 4 診斷 ──▶ 5 出稿
   gate_check       composer.py     模型        selfcheck    depth_check  run_pipeline
   （13 項）        （機械注入知識）  （只補【填】）（不過即停） （只看報告） （唯一出口）
```

| 步 | 一步的命令 | 過不了會怎樣 |
|---|---|---|
| 0 | `python scripts/gate_check.py gate.json` | 缺項 → 禁止產出任何方案內容 |
| 1 | `python scripts/composer.py --rules rules.json --out skeleton.md --tier 标准` | 解析失敗 → 退出碼 2 |
| 2 | （模型補 `【填】`，本地化為簡體） | 殘留 `【填】` → 第 3 步自檢判硬錯誤 |
| 3 | `python scripts/selfcheck.py plan.md` | 任一硬錯誤 → 退出碼 1，不得交付 |
| 4 | `python scripts/depth_check.py plan.md` | 只診斷，不阻攔 |
| 5 | `python scripts/run_pipeline.py --rules r.json --budget b.json --plan plan.md -o 方案.docx` | 任一關不過 → 不生成 `.docx` |

## 步驟 0 · 收資料與門禁

- **輸入**：客戶口述／Brief
- **動作**：按 `SKILL.md §0` **門禁 13 項一次問全**（含目標字數）；用戶每次糾偏＝規則表升級
- **命令**：`python scripts/gate_check.py gate.json`
- **產出**：`任務規則表.json`（`client` ＋ `gate` 15 欄 ＋ `delivery`，末行 `rules_table_confirmed: true`）
- **校驗**：`gate_check` 退出碼 0；規則表已請用戶確認

## 步驟 1 · 組裝骨架（本 skill 的核心 · 知識在這裡被強制注入）

- **輸入**：`任務規則表.json`
- **命令**：
  ```bash
  python scripts/composer.py --rules rules.json --out skeleton.md --tier 标准 --top 5
  #  --tier  速览 | 标准 | G端        --top  打法條數（3–7）
  ```
- **腳本做了什麼（確定性，非模型生成）**：
  1. 解析 `00-打法库` 的**全部 §X.Y 打法**（含「什麼情況用／怎麼做／怎麼驗收／案例」）
  2. 按 **`SKILL.md §二 狀況→打法 路由表`**（編碼在 `scripts/knowledge_map.json`）匹配客戶狀況 → 選 3–7 條打法
  3. 對每條打法**自動拉取**：具體動作（怎麼做）＋驗收指標＋可抄案例（`cases/NN-*.md`）
  4. **注入「理論依據」**：打法 → `knowledge_map.json` → `03` 模型碼 ＋ `49` 書籍（每條打法都掛 `打法库 §X.Y`）
  5. 按檔位輸出骨架（`速览`／`标准`／`G端`）
- **產出**：`skeleton.md`（打法／理論依據／可抄案例**已注入**；其餘 `【填】` 待補）
- **校驗**：composer 輸出**天然過 `selfcheck` 第【7】【8】關**（可立即跑一遍確認）

## 步驟 2 · 填空（模型唯一的活）

- **輸入**：`skeleton.md`
- **動作（只做三件）**：
  1. 補 `【填】` 處：**卡點重構句**（「不是 X——是 Y」）、**KPI 目標數字**、**預算明細**（分項加總＝合計）、**風險四件套**（每條掛「模式 NN」）、**自檢單** 逐項 ✅
  2. 把注入的**繁體原文本地化為簡體**，並逐字對照禁用詞表
  3. ⛔ **不得刪改注入的打法／理論依據／可抄案例** —— 那是 skill 的強制輸出
- **產出**：`plan.md`
- **校驗**：`grep -c "【填】" plan.md` 應為 **0**

## 步驟 3 · 交付前自檢

- **命令**：`python scripts/selfcheck.py plan.md`
- **產出**：八類檢查報告（結構／自檢單／內部文檔／可信度／五要素／禁用詞／核心方法論／**知識庫強制引用**）
- **校驗**：**退出碼 0**（任何 ❌ 硬錯誤＝不得交付）

## 步驟 4 · 深度診斷（只診斷，不阻攔）

- **命令**：`python scripts/depth_check.py plan.md`
- **產出**：9 維度報告（競品／風險四件套／KPI 預警線／物料／禁用詞／重複度／空話詞…）
- **校驗**：無（**改不改由你決定**）

## 步驟 5 · 出稿（唯一出口）

- **命令**：
  ```bash
  python scripts/run_pipeline.py --rules rules.json --budget budget.json \
      --plan plan.md -o 方案.docx --title "客戶名 營銷方案" --date 2026-09-16
  ```
- **產出**：`.docx`（封面＋目錄＋正文＋頁碼）
- **校驗**：**拿不到 `.docx` ＝ 沒完成**（它必跑 selfcheck，不過就拒絕生成）

## 三檔交付對照

| 檔位 | 對象 | 產出重點 | composer 參數 |
|---|---|---|---|
| **速覽** | 小微企業／個案 | 一頁看懂打法：卡點＋3–7 條打法＋預算量級 | `--tier 速览` |
| **標準** | B端客戶 | 完整八篇方案（診斷／策略／定位／觸達／文案／KPI／預算／風控） | `--tier 标准` |
| **G端** | 政府／公共項目 | 標準版 **＋** 政策依據與項目背景 ＋ 匯報稿/評審口徑 ＋ 合規與輿情紅線 ＋ 公文格式規範 | `--tier G端` |

## 為什麼這樣設計（回應「模型做不到強制使用」）

> **舊做法**：模型讀 `03`/`00`/`cases`，自願引用 → 相當於 prompt / RAG，模型可以整篇不引用。
> **新做法**：`composer.py` **機械把知識選出來、注入進骨架** → 模型拿到手的骨架裡「打法＋模型＋學者＋案例」**已經在了，刪不掉**。
> **兜底**：`selfcheck` 第【8】關再校驗一遍（不過＝不出稿）。規則可以假裝讀過，**退出碼假裝不了**。

## 附 · 策劃案的「打法與實操」規範（用戶 2026-09-16 硬要求）

> 用戶原話：「策劃具體操作流程還是沒寫好，要詳細精準到每一步 —— **指策劃案的打法和實操**。」

- 每條打法的「具體動作」**必須拆成編號步驟，≥3 步**；每步寫齊：`動作 ｜ 時間 ｜ 誰做 ｜ 物料·話術 ｜ 產出`
- 只寫一句話（如「印 500 張包裹卡」）＝不合格
- 這一步**由 `composer.py` 自動生成骨幹**（拉 `00-打法库` 的「怎麼做」拆成步驟）；模型只補 時間／物料／數字
- `selfcheck` 第【7】關機械校驗：任何一條打法不足 3 個編號步驟 → **硬錯誤、不出稿**
- 標杆示範：`references/范例/便利店开学季战役-交付稿.md`（7 條打法全部逐步驟）

## 維護注意

- 改「哪種狀況用哪條打法」→ 改 `scripts/knowledge_map.json` 的 `路由规则`（不要在 SKILL.md 寫文字）
- 改「打法 → 理論依據」→ 改 `scripts/knowledge_map.json` 的 `major_theory` / `play_overrides`
- 改檔位結構 / 新增 G端規範產物 → 改 `scripts/composer.py` 的 `build_skeleton`
- 改完**必做雙向驗證**：① 標杆範文 `selfcheck` 過（exit 0）② 造一份違規稿 `selfcheck` 攔（exit 1）
