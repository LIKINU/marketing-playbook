## 一、为什么有这一篇（一次真实事故）

2026-09-17，一个某真实交付项目经历多次重做——**内容没错，形状错了**：

| # | 坑 | 后果 | 对应铁律 |
|---|---|---|---|
| 1 | 用自己的方法论章节结构，**替换**了主办方模板 | 整份重排 | 铁律 1 |
| 2 | 把用户给的**大纲溶解**进模板小节，大纲章节名全部消失 | 整份重排 | 铁律 2 |
| 3 | 为了「证明我按你要求做了」，加了一节《章节组织方式》对应表 | 被判「跟报告无关的东西」，再清一遍 | 铁律 3 |

**一句话总结**：形状错一次 ＝ 整份重做 ＝ 额度与情绪双重浪费。**先锁形状，是最省的做法。**

> 这类任务的最大成本不是「写」，而是「返工」——**内容错了改一段，形状错了整份重做。** 所以必须**先锁形状，再写内容**。以下规则优先级高于一切写作技巧。

## 二、6 条铁律

### 铁律 0 · 先交目录，不交正文
- 第一版**只输出一页目录**：只写标题层级（一级／二级／三级），不写任何正文、不写表格、不写数据。
- 目录后附一句：「确认目录后我再填正文。你也可以直接改标题，改完我照新版填。」
- **收到确认前，禁止生成正文。** 目录改一次的成本是分钟级，正文改一次是小时级。
- 唯一例外：用户明确说「直接给我完整版」时，才跳过本条。

### 铁律 1 · 给定结构，标题一字不改
- 若用户／主办方／招标方提供了模板、大纲或目录，**一级与二级标题必须逐字沿用**：
  不得替换成「更好听」的说法、不得合并、不得拆分、不得重排顺序、不得自造层级。
- 模板自带的板块名（哪怕看起来平淡）**也一个字都不能动**。
- 模板未覆盖但要求必须有的内容 → 作为**新增同级或下级章节**补进去，而不是改造原有标题。
- 若模板说明里写了「仅供参考，可调整」，**默认仍按原样保留**——除非用户明确要求改。

### 铁律 2 · 用户给的素材要「可见地插进去」，不能溶解
- 用户给了自己的大纲／章节清单时，这些章节必须作为**文档中真实存在的可见章节**出现，
  **保留它原本的章节名与编号**（如「一、活动背景」「4.2 核心活动模块」）。
- ⛔ 禁止把用户大纲的内容打散、揉进别人模板的小节里——**那等于用户的大纲消失了**。
- 位置可以按逻辑排，但**章节名与编号要在正文里看得见**。

### 铁律 3 · 交付稿禁带内部物
以下内容一律**不进交付稿**，只留在聊天回复或内部备份里：
1. 章节组织方式说明、结构映射表、对应关系表、组织原则说明；
2. 一切位置标注：「（本方案补充）」「【原文】」「（对应第 X 章）」「（模板第 X 节）」等；
3. 内部知识库坐标：模型编号、打法库编号、案例库路径、失败归因编号、作者库编号；
4. 交付自检单、门禁清单、分工记录、裁决记录、事实底稿索引；
5. 「本报告的章节组织方式」「我们的思路是」「为了让评审看到」这类自证／说明性文字；
6. 团队内部争论过程（**可以保留结论与反对理由**，但不要写「团队讨论中多数人认为…我方反对」）。

> 判断标准一句话：**这份内容，读者拿它做决定时是否需要？不需要的，全部删。**

### 铁律 4 · 改结构必改引用与编号
- 任何一次标题重排、层级调整、章节移动之后，**必须立刻复查并修复**：
  · 正文里所有「见 X.X 节」「第 X.X 节」的交叉引用；
  · 所有多级标题编号是否连续、是否与所属上级匹配（**不要出现 3.0 这种断号**）；
  · 目录、页眉、附录序号是否同步。
- 这一步不做，交付稿会出现「指向不存在的章节」这种**一眼可见的硬伤**。

### 铁律 5 · 数字必须有来源，禁止编造
- 每个数字都要能指到源头文件／公开报告；查不到就写**定性表述**或标注「**假设／待验证**」，
  **绝不为了让表格好看而补一个数字**。查不到依据的功能或数字，宁可不写。

## 三、4 条结构性根因（为什么 AI 会「不听」）

> 这 4 条不是「态度问题」，是**结构问题**。照抄一份 PROMPT 只能补一版；
> 理解这 4 条，才能解释「为什么反复交代还是反复犯」。

| # | 机制 | 一句话 | 对策 |
|---|---|---|---|
| 1 | **skill 文件在系统层「更近」** | 上下文里塞入了 skill 全文与关键词，AI 会默认它比用户当面说的话优先级更高 | 在 SKILL.md 顶部写死**最高优先级条款（P0）**：用户给定结构 > skill 一切默认 |
| 2 | **「skill 自检全绿」被当成了成功标准** | AI 把「符合 skill 默认交付标准」当成「用户目标达成」，自检一绿就交 | 明写**「本 skill 自检通过 ≠ 交付达成」**；用户自定义验收项必须另行逐条核对并输出 |
| 3 | **「内容写完」被等同于「你要做的事做完」** | AI 把「方案成形」当目标，而不是「按你给定结构成形」→ 替换模板、溶解大纲 | 铁律 1 + 铁律 2；形状类任务先交目录 |
| 4 | **长输出绑架了后续判断** | 已写了几千字，拆掉重来变成心理成本 → 宁愿修补也不重排 | 第一版只追求「**形状对**」，不追求「完整、惊艳、篇幅长」 |

> 第 4 条最隐蔽：它不是「不懂」，而是「**沉没成本**」。所以「先锁形状」不只是省事，是**打断沉没成本的形成**。

## 四、交付前自检 8 项（**必须真的跑，并把结果原样输出给客户**）

| # | 检查项 | 结果 | 依据 |
|---|---|---|---|
| 1 | **结构**：一级／二级标题是否与给定模板逐字一致？用户大纲是否作为**可见章节**存在？ | | |
| 2 | **内部物**：按铁律 3 的 6 条逐条扫一遍，命中就删。 | | |
| 3 | **交叉引用与编号**：是否全部指向真实存在的章节？编号是否连续？ | | |
| 4 | **硬性格式**：封面要素、题目长度、字数、文件双格式、必交附件，逐项核对。 | | |
| 5 | **合规与匿名**：禁用词、身份信息（姓名／学号／学校／指导教师）是否出现。 | | |
| 6 | **排版规格**：若对方给了字体字号行距要求，是否真的套用到了**成品文件**上。 | | |
| 7 | **数字来源**：关键数字是否都有出处。 | | |
| 8 | **声明项**：AI 使用说明、原创性声明等对方要求的内容是否已写。 | | |

> 输出格式：一张表，每行「检查项 ｜ 结果 ✅/❌ ｜ 依据」。**有 ❌ 就先修，修完再交。**

## 五、工作节奏

- **不要在第一版就追求「完整、惊艳、篇幅长」。第一版只追求「形状对」。**
- 用户说「重写一份」时，**先确认是哪一层错了**：是内容错（改段落）还是形状错（改目录）？
  **问清再动手，不要默认推翻全文。**
- 一句话里含有**两个约束**时（如「用官方模板」＋「也要有大纲十章」）：动手前**把两个约束分别复述一遍**再动手，
  避免只听进去一个、另一个被自己的默认吞掉。
- 每一轮结束时，用一句话说明「**这一轮改的是哪一层**」，让用户知道进度到哪。

- 本协议的 **P0 最高优先级条款**（写在 `../SKILL.md` 顶部）**优先于** SKILL 的协议 1–8 与本文件其余内容。
- 铁律 1／2 是 SKILL「协议 2 · 结构冲突合并不取舍」的**强化版**：协议 2 管「内容不丢」，铁律 1／2 额外管「**标题与用户大纲原样保留、可见**」。

## 七、这 8 项现在由哪些脚本机械跑（2026-09-17 补齐）

> 为什么补这一节：这 8 项原来只能**人工**逐条比。人工比的东西，做十遍就会漏一遍 ——
> 而且漏的那一遍不会有任何报错。能机械化的部分全部下沉到脚本，只把真正需要判断的留给人。

| 自检项 | 谁在管 | 怎么跑 |
|---|---|---|
| 1 结构（模板逐字一致／用户大纲可见） | `structure_fix.py`（体检）＋ 人工比对模板 | `python scripts/structure_fix.py plan.md` |
| 2 内部物 6 条 | `selfcheck.py`【3】【10】 | 随 `run_pipeline` 自动跑 |
| 3 交叉引用与编号 | `selfcheck.py`【13】（硬错误）＋ `structure_fix.py --renumber`（修） | `python scripts/structure_fix.py plan.md -o fixed.md --renumber` |
| 4 硬性格式（封面／文件名／必交附件） | `delivery_check.py` | `python scripts/delivery_check.py --dir 交付目录 --init` |
| 5 合规与匿名（禁用词／身份信息） | `selfcheck.py`【6】＋ `delivery_check.py` 封面禁项 | 同上 |
| 6 排版规格（字体字号行距） | `build_docx.py` 落样式；`delivery_check.py` 只能查封面，**字号需人工抽检** | — |
| 7 数字来源／引用用脚注 | `docx_footnote.py`（装真脚注）＋ 人工核来源 | `python scripts/docx_footnote.py 方案.docx --list --verify` |
| 8 声明项（AI 使用说明／原创性声明） | **人工**（每家的叫法不同，不适合硬编码） | — |

**一条原则**：脚本查「能否证自己的事实」（引用指得到吗、附件在不在、占位符还在不在），
人查「需要判断的东西」（这份声明够不够、这个数字能不能用）。**不要把该机械的留给人，也不要把该人判断的硬编码成脚本。**
