# 全库质检报告（2026-09-14）

> 审计范围：`marketing-playbook/` 全库（SKILL.md、AGENTS.md、README.md、references/ 全部文件、references/archive/机构档案/、scripts/ 四个脚本）
> 审计方式：逐行阅读 + 全库交叉引用扫描 + 脚本实测（构造 12 组测试输入，含正常/边界/恶意/空洞输入）
> 审计结论只出报告，未改动任何文件。
> 实测环境：macOS / Python 3（本机未安装 `python-docx`，故 `build_docx.py` 的 Word 渲染路径为静态审查 + 拒绝生成路径实测）

## 一、总体评估

**这套 skill 的「知识层」健康度明显高于「规范层」，而「规范层」又高于「脚本层」——问题几乎全部集中在「说完之后有没有人真的做得到」这一环。**

- **知识资产扎实**：18 个行业案例集、104 条打法（实测 104，正确）、63 个模型（实测 63，正确）、26 号失败归因库（12 模式 + 34 条预演，实测正确）、31 号小企业手册（55 条零预算打法 + 16 模式，实测正确）都名副其实，且普遍带可信度标注与「查不到的部分」诚实清单——这是全库最值得保留的部分。
- **规范层已经「改过 4 轮」，但每次改都只改了主入口，没回头改旁证文件**：门禁 12→13 项、字数「≥2 万字」→「5,000–10,000 字」、协议 5 条→8 条，这三处改动都留下了 3–5 处旧说法（README、12 号模板、SKILL.md 自己的变更记录）。协议条数在三个文件里分别是 8 / 7 / 5，**用户按 README 数会数出 7 条**。
- **脚本层存在 1 个 P0 级死循环**：`selfcheck.py` 把 SKILL.md 明令必備的「附件 C 事實底稿」当成违规泄漏词拦下，同时要求在 plan.md 里出现「自檢單」字样（而协议 3 要求自检单输出在**聊天回覆**里）——**按规范写的稿子 100% 过不了校验，`build_docx.py` 就永远拒绝生成 `.docx`**。这直接击穿了全库反复宣称的「拿不到 .docx ＝ 没完成」这一唯一强制点。
- **另外三个脚本的正确性也有实质缺陷**：`gate_check.py` 实测能被「没有 / 无 / 暂无 / 不自适用 / - / 0」这类空洞答案骗过 12/13 项；`budget_check.py` 对「項目|單價|數量|小計」四列表、多张预算表、以及「3 萬」这种中文单位——三种最典型的写法全部误判，而 SKILL.md §二 路由表自己就用「5 千–5 萬」。
- **一句话：知识层已经可用，规范层需要一次「一致性收口」，脚本层需要一次「重写 + 与规范对表」。** 在脚本修好之前，建议把协议里的「拿不到 .docx ＝ 没完成」改为「校驗不過須留痕說明」，否则 AI 会被这套工具卡死（而协议 8 又说「强制不得变成卡死」——脚本正在制造协议 8 明令禁止的结果）。

## 二、问题清单

### P0 —— 会直接导致执行出错 / 流程卡死

**[P0-1] `selfcheck.py` 把 SKILL.md 明令必備的「事實底稿」判为硬违规 → `build_docx.py` 拒绝生成 → 死循环**
- 位置：`scripts/selfcheck.py:41-44`（`INTERNAL_LEAK_HARD` 含「事實底稿」/「事实底稿」）↔ `SKILL.md:301`（附件 C = 事實底稿，属交付物必備結構）↔ `SKILL.md:52`（自檢單第 3 項「文檔結構完整（八篇＋附件…）」）↔ `SKILL.md:366`（build_docx「內部先跑 selfcheck，不過就拒絕生成 .docx」）
- 实测证据：构造一份**完全符合 SKILL.md §三 規範**的 plan.md（執行摘要 + 八篇 + 附件 C 事實底稿），`python3 scripts/selfcheck.py plan_full.md` → `EXIT=1`，硬錯誤明列 `交付稿混入內部過程字樣：事實底稿`；随后 `build_docx.py` 一律拒绝出稿。
- 影响：**越按规范写，越出不了稿。** 执行 AI 只有两条路：① 删掉附件 C（违反 §三）；② 用 `--force` 跳过（等于废掉唯一强制点）。这是全库最严重的缺陷。
- 建议修法：区分「词」与「语境」——把「事實底稿」从 `INTERNAL_LEAK_HARD` 移出，改为**只在它出现在「第一篇～第八篇正文」范围内才报警**（附件区豁免）；或在 §三 把附件 C 改名（如「附錄 C · 客戶原始情況與約束」）并同步全库。二者择一，必须同步。

**[P0-2] `selfcheck.py` 要求「自檢單」出現在 plan.md 內，但协议 3 要求它輸出在「交付回覆」中 → 按规范做必不过校验**
- 位置：`scripts/selfcheck.py:119-126`（`has_checklist = ("自檢單" in text or "自检单" in text)`，不在 plan.md 里就 `hard_errors.append`）↔ `SKILL.md:46`（「必須**在回覆中**逐項輸出下表」）↔ `SKILL.md:383`（「原樣輸出**在回覆中**」）↔ `scripts/selfcheck.py:216`（脚本自己的收尾提示也写「請把 12 項《交付自檢單》原樣輸出在**交付回覆中**」）
- 实测证据：`plan_full.md`（含八篇 + 附件 C、無自檢單）→ `EXIT=1`，硬錯誤 `未輸出 12 項《交付自檢單》`。
- 影响：与 P0-1 叠加，构成**双重必然失败**。反过来若 AI 为过校验把自检单塞进正文，这份带 12 行 ✅/❌ 的表会被 `build_docx.py` 渲染进**给客户的 Word 交付稿**里，违反协议 5「交付形态红线」（用户要的是作品，不是工作过程）。
- 建议修法：`selfcheck.py` 增加 `--checklist` 参数或 `--reply-checklist` 开关；默认不要求 plan.md 含自检单，改为「要求交一份 `checklist.md`/`checklist.json`」或「由 build_docx.py 从参数读取已输出标记」。同时正文渲染前应剔除自检单区块。

**[P1-8] `gate_check.py` 会被空洞答案骗过（is_filled 白名单过窄）**

- 影响：门禁是全库第一道也是最重要的一道闸（协议 1），却能用一个「无」字骗过。而 SKILL.md:114 明写「不准用『一般情況』代替」——脚本没有能力执行这条。
- 建议修法：`bad` 扩为「空值 + 否定式 + 未定式」三类，至少加入：`无/沒有/没有/暂无/暂无/不适用/不知道/不清楚/没想过/没做过/没定/待定/未定/待确认/TBD/-/—/N/A/0/无数据`；并加一条**最短长度阈值**（如 <4 字直接判为未填，因门禁答案必然长于 4 字）。

- 建议修法：改为「精确键名优先，别名匹配降级为人工确认提示」；对同一条目的多个候选命中要求唯一且不冲突；把未匹配字段的多余提示（`:124-126`）从 `ℹ️` 提示升级为**必须人工确认**的阻断项。

**[P1-10] `budget_check.py` 的 Markdown 解析对三种最常见的写法全部误判**
- 位置：`scripts/budget_check.py:52-74`
- 实测证据（三组）：
  1. **四列表**：`| 項目 | 單價 | 數量 | 小計 |` + 合計行 → 脚本只取第 2 格（單價）相加，得出 `分項加總 4,003`（正确应为 9,500），合計行因单元格错位未识别 → **误报「沒有填合計欄位」**
  2. **多张表**：文档同时有「7.1 預算總表」和「7.3 分月支出」两张 `| 項目 | 金額 |` 表 → 脚本把**所有表的所有行**合并相加，得出 `22,000 vs 11,000` → **误报「對不上！差額 +11,000」**（实际上是两张不同口径的表）
  3. **中文单位**：`| 物料 | 3 萬 |` → 正则只剥离 `[¥￥$,\s元]`，不认「萬」→ 解析不到任何行 → **直接报「找不到可解析的預算表」**
- 影响：SKILL.md §二 路由表自己的预算列就写成「5 千–5 萬」「1–10 萬」，而绝大多数中文方案预算表都用「萬」——**这个脚本在真实稿件上的误报率会很高**，而后果是「不準交付」（SKILL.md:364）。用户侧只会看到「卡住了」。
- 建议修法：① 增加「萬/万/千/K/w」单位解析；② 只解析**标题含「預算/總表/合計」的那一张表**，或提供 `--table-index`；③ 表头列名做语义识别（識別「小計/金額/費用」列而非死取第 2 格）；④ 把所有不确定情形降级为 `⚠️ 需人工確認`，不要直接判 `❌ 不通過`。

**[P1-11] `selfcheck.py` 完全不检查「附件 A–D」，而规范把附件列为必備**
- 位置：`scripts/selfcheck.py:28-38`（`SECTIONS` 只有 9 项：執行摘要 + 八篇，**无附件项**）↔ `SKILL.md:298-302`（附件 A 物料文案 / B 話術表 / C 事實底稿 / D 參考案例）↔ `SKILL.md:52`（自檢單第 3 項「八篇＋附件」）

### 4.4 闭环结论

> SKILL.md:368 宣称「交付物只能由 build_docx.py 產出，而它必跑自檢 —— 拿不到 .docx ＝ 沒完成，AI 繞不過」。

**实测结论：这个闭环目前是断的，而且是「逆向断」——正常流程走不通，只能靠 `--force` 绕。**
- 按 §三 规范写 → 含「事實底稿」→ 被 selfcheck 判违规（P0-1）
- 按协议 3 把自检单放在回覆里 → plan.md 里没有「自檢單」→ 被 selfcheck 判违规（P0-2）
- 两条硬错误同时触发 → `build_docx.py:230-235` 拒绝生成 → 用户拿不到 `.docx`
- 唯一出路是协议 8 的 `--force` —— 而这恰好是「拿不到 .docx ＝ 沒完成」这句口号要防的行为

**因此 P0-1 与 P0-2 必须最优先修，否则整套脚本强制层不但无效，还会稳定地把合规交付卡死（正好落在协议 8 开篇「一個把人卡死的流程，比一個寬鬆的流程更糟」所禁止的情形上）。**
