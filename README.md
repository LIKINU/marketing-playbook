## 一、用它之前要知道的一件事

**它會先問你一堆問題，問完才動手。**

這是刻意設計的。沒搞清楚客戶情況就出方案，等於算命。所以第一次使用時：

1. 它會對照 **13 項門禁清單** 逐項核對，列出你還缺哪些信息
2. 一次性把缺的問完（不會擠牙膏）
3. **產出《任務規則表》請你確認**（門禁答案＋交付結構＋紅線）
4. **你確認之前，它不會出任何方案內容**

13 項門禁：賣什麼／賣給誰／現在規模／卡在哪／預算／現有資源／時間死線／硬約束／決策人／競爭對手／過去試過什麼／怎麼算成功／**目標字數**。

> **為什麼有「目標字數」這一項**：比賽提交、招標文件、客戶模板常有字數或頁數上限。先問再寫，比寫完再砍划算。

## 一點五、最高優先級條款（P0）＋ 八條強制協議（違反任何一條＝這次使用失敗）

> ⛔ **P0 · 優先於下面八條，也優先於 skill 的一切默認結構。** 由 2026-09-17 一次真實返工事故反推（一個校園大賽項目書 **1.5 萬字重做多次**）。
> 完整版見 `references/11-防返工交付协议.md`（6 條鐵律 ＋ 交付前自檢 8 項 ＋ 4 條結構性根因）。

| P0 | 條款 | 白話解釋 |
|---|---|---|
| **P0-1** | **你給的結構 > skill 的一切默認** | 你（或主辦方）給了模板／大綱／目錄／提交清單時，**它的優先級高於 skill 的默認八篇結構**。一級二級標題**逐字沿用**：不改寫、不合並、不拆分、不重排、不自造；模板沒有的內容**新增章節**補進去，而不是改造原標題 |
| **P0-2** | **你的素材要「看得見地插進去」** | 你給的大綱必須作為**文檔中可見章節**出現，保留原名與編號（如「一、活動背景」）；⛔ 不許打散揉進別的小節——**那等於你的大綱消失了** |
| **P0-3** | **「skill 自檢通過」≠「交付達成」** | skill 的自檢只查它自己 care 的項，**不查「有沒有用你給的模板標題」**。你的驗收項（格式／字數／匿名／雙格式／附件）必須**另行逐條核對並輸出**——不許拿「自檢全綠」當「可以交了」 |
| **P0-4** | **形狀類任務先交 1 頁目錄** | 涉及結構／粒度／組織方式時，**第一版只交一頁目錄**，你確認後才寫正文；一句話含兩個約束 → 動手前**分別複述** |

> **一句話根因**：所有返工都源於「先默認生成全文當第一版」，而不是「**先鎖形狀**」。

| # | 協議 | 白話解釋 |
|---|---|---|
| 1 | **啟動即立規** | 問完就出一張《任務規則表》給你確認；**你之後每次糾偏＝規則表升級**，它要先複述再動手，不許當一次性修補 |
| 2 | **結構衝突「合併，不取捨」** | 你若有指定格式（比賽清單、客戶模板），它會把該寫的內容**映射進去，硬要素一件不丟**；不許為了貼合格式砍深度 |
| 3 | **交付前自檢單原樣輸出** | 說「完成」之前，必須在回覆裡逐項打出 12 項自檢單並標 ✅/❌；有 ❌ 就不許說完成 |
| 4 | **工具盤點先於路徑** | 要讀外部資料時，**先盤點已連接的連接器／API**，能用連接器就不許用爬蟲硬繞（燒額度主因）；付費生成先報價 |
| 5 | **交付形態紅線** | 對外一律**簡體 `.docx`**；**內部過程文檔（事實底稿／Agent 分工／裁決記錄）不得混進交付稿** —— 你要的是作品，不是工作過程 |
| 6 | **每輪開頭輸出《流程狀態》行** | 它每輪回覆第一行必須是：`【營銷方案 · 流程狀態】門禁 13 項：x/13（缺：…）｜ 任務規則表：…｜ 當前階段：…`。**缺了這一行，就代表它跑偏了** |
| 7 | **跨平台一致** | 不許依賴某個平台的特有能力；能力不足要降級（例如不能派多 Agent 就順序扮演），**但降級不等於跳步** |
| 8 | **卡死處理（不許把自己卡死）** | 同一項校驗**連續 2 次不過 → 停止重試**，把問題攤給你、給你 2–3 個選項選；腳本報錯或環境不可用 → **降級成 Markdown 繼續產出**；跳過一律**留痕**（明說哪幾項沒檢查）。**不許**同一錯誤重試超過 2 次、不許因校驗不過就不交付、不許靜默跳過 |

> 這八條不是口號：執行 AI 最常見的五個失敗模式（骨架式使用／跳過自檢／門禁漏項／工具慣性繞路／結構衝突做減法）都在 `references/04-失败归因总库.md` 附錄，每條協議各自堵住一個。

## 一點七、怎麼一眼看出它有沒有照做（你只需看 3 處）

| 看哪裡 | 正常 | 有問題 → 你怎麼說 |
|---|---|---|
| **回覆第一行** | 有 `【營銷方案 · 流程狀態】…` | 沒有這行 → 「**你沒輸出流程狀態**」（它必須補上並回到正確階段） |
| **動筆之前** | 先問你問題（門禁 13 項）→ 出《任務規則表》等你確認 | 直接開始寫方案 → 「**先出任務規則表**」（強制走協議 1） |
| **說交付之前** | 原樣輸出 12 項自檢單並標 ✅/❌ | 只說「已完成」→ 「**把 12 項自檢單打出來**」（強制走協議 3） |

**這三句話就是你的保險**（記住就夠，不必每次說）：

1. 「你沒輸出流程狀態」
2. 「先出任務規則表」
3. 「把 12 項自檢單打出來」

> 正常情況下協議會自動生效，這三句是兜底。但 AI 是機率性的 —— **你手上有這三句，它就沒有跑偏的空間。**

**想要更硬的話**（可選）：在支持 hook 的平台（WorkBuddy／Claude Code）可以加裝一個 Stop 鉤子，AI 想結束回答時自動檢查自檢單，沒輸出就攔住。配置方法見 `AGENTS.md` §九 —— **但這是選配，不影響跨平台使用。**

## 一點八、卡死了怎麼辦（重要）

**校驗是為了讓交付更好，不是為了讓交付不出來。** 如果它卡住不動了，按症狀處理：

| 症狀 | 你怎麼說 |
|---|---|
| 反覆改同一處、來回好幾輪 | 「**卡在哪了？把錯誤原文貼出來**」→ 它必須把問題攤開，並給你 2–3 個選項選 |
| 跑腳本報錯、環境不對（沒裝套件等） | 「**降級：不用腳本，直接出 Markdown**」→ 它應該繼續產出，並註明哪部分未經校驗 |
| 校驗過不了但你不想再等 | 「**跳過這項，先出稿**」→ 允許用緊急出口出稿，但**必須標明哪幾項沒過校驗** |
| 完全沒反應（對話太長／工具超時） | 開個新對話，說「繼續上一個營銷方案，上次停在 X」 |

**它的三條紅線**（你可以據此要求它）：

1. 同一個錯誤**不許重試超過 2 次**
2. **不許因為校驗不過就不交付**（卡住必須上報，不能自己死磕）
3. **不許靜默跳過校驗**（跳過必須告訴你跳了哪幾項）

> 一句話：**卡住就讓它上報，別讓它自己死磕。**

> 想跳過？只有明說「先按假設出一版」才行 —— 這時文檔首頁會標註「本方案基於未經驗證的假設」並列出假設清單。

| 三 · 定位与口径 | 先把話說對，再想怎麼說出去。 |
| 3.1 定位与差异化支点 | 一句定位語，加三個支點 —— 每個支點後面跟一個能查證的事實。 |
| 3.2 禁用词与红线 | 逐條列出絕不能說的話，並當場給出替換說法。 |
| 3.3 对不同人说什么 | 按角色分口徑 —— 同一件事，對不同人說不同的一句。 |
| 四 · 触达与渠道 | 渠道選擇要同時寫「為什麼用」和「為什麼不用」。 |
| 五 · 落地文案与物料 | 物料清單（放哪／寫什麼／多少錢）＋ 一線話術（能直接念出口）。 |
| 5.1 同一母题 · 各渠道的**不同形态** | 证明这是「渠道原生」而不是「同一段内容换个渠道名」。 |
| 六 · KPI 与追踪机制 | 只追蹤能立刻拿到的幾個數，並定好什麼時候改。 |
| 七 · 预算明细 | 分項預算表 ＋ 盈虧線測算。 |
| 7.2 盈亏线测算 | 算出「做到多少就不虧」，讓客戶知道風險有多大。 |
| 7.3 敏感性分析 | 关键结论不给区间＝假精确。盈亏线是单点值时必须给三档。 |
| 7.4 投流计划 | 投流的闭环：出价＋素材迭代＋止损。缺了止损，客户只能凭感觉加码或收手。 |
| 7.5 追投与止损规则 | 动态止损。敏感性分析是静态三档，这一节回答「第 3 天不达标，谁在第几天前决定调什么」。 |
| 八 · 执行与风控 | 把方案落成「誰在哪天做什麼」，並寫清風險與邊界。 |
| 8.1 行动清单 | 一行一件事，做成可打勾的表。 |
| 8.2 执行人力检查 | 人力不夠時先砍什麼 —— 寫清刪減順序。 |
| 8.3 风险清单 | 每條風險寫四件套，缺一件就不算寫完。 |
| 8.3.1 超卖与履约兜底 | 承诺了优惠却发不出货，是最典型的信任崩塌点。方案里必须写「超卖了怎么办」。 |
| 8.3.2 退款与纠纷升级路径 | 退换货规则与投诉升级路径不写，一线会自己乱来。 |
| 8.3.3 差评与口碑预案 | 投放必然带差评。没有规矩，一线会私了、会删评、会和用户吵起来。 |
| 8.3.4 资产与账号风险 | 私域案的头号事故：员工离职带走客户名单、主账号被封。 |
| 8.4 关键假设与验证 | 列出方案成立所依賴的假設，並寫明怎麼驗、錯了怎麼辦。 |
| 8.5 待解决问题清单 | 坦白列出還沒定的事，並標明誰定、什麼時候定。 |
| 8.6 不承诺的事 | 劃清邊界：哪些結果本方案不保證。 |
| 8.6.1 舆情升级与对外发声 | 出事了谁说话、多久内说。不写，危机时只能临场找老板。 |
| 8.6.2 被举报与判罚的应对 | 3.2 只写了「预防违规」，这一节写「**被举报之后**怎么办」。 |
| 8.7 这个方案最可能怎么死 | Red Team：方案先被自己攻击一轮，而不是等客户来问。 |
| 8.8 制作可行性与档期 | 做得出来才算方案。排期要从 DDL 倒推，不是从发布日正排。 |
| 8.9 外部合作合同要点 | 达人塌房、删稿、数据造假的责任要在合同里落，否则品牌连坐却无追偿依据。 |
| 8.10 授权与素材来源 | 出事时拿得出东西的那一页。全库「授权／版权」有 30 处，却没有一处落在交付稿的必需字段里。 |
| 8.11 复盘节点 | 分阶段复盘：异常要在第 3 天就被看见，而不是拖到结案。 |

**篇幅**：以《任務規則表》確認的**目標字數**為準（未指定時預設 **5,000–10,000 字**）。深度看「硬要素齊不齊」（五要素行動、禁用詞口徑、預算能對上、KPI、人力檢查、假設驗證），**不靠字數注水，也不為省字砍內容**。

## 四、它內部怎麼工作（六步）

```
第 0 步 門禁 ──── 13 項問清，沒問清不出方案
第 1 步 事實底稿 ── 把客戶告知的一切整理成唯一輸入源
第 2 步 現狀分析 ── 體檢（數據事實 + 我的判斷 + 已排除的假設）
第 3 步 多 Agent 分工 ── 策略 / 品牌 / 觸達 / 文案 / 財務風控，各寫各的
第 4 步 主理人裁決 ── 衝突裁決 + 合併成稿 + 跑自檢
第 5 步 交付 Word ── 生成 .docx
```

**多 Agent 分工（每次都走）**：
各 Agent **只讀事實底稿、不互讀草稿**（避免互相遷就、越寫越像）；衝突由主理人裁決並記錄理由。

> ⚙️ **腳本鏈（真正的強制層）**：`python scripts/flow.py` 看流程狀態 → **`composer.py` 把打法／模型／學者／案例
> 機械注入骨架**（知識繞不過）→ 模型只填空 → `selfcheck.py`（不過關不出稿）→ `run_pipeline.py`（唯一出口）。
> 逐步操作手冊見 `references/08-操作流程SOP.md`。

## 六、交付前它會自己檢查（**18 關，全機械**）

> 完整清單見上面 §0.3。這裡只講**給你看的四類**：

- **數字**：預算分項加總對不對？盈虧線算得對不對？【未核實】數據剔除了嗎？
- **執行**：每條動作有「誰做」嗎？負責人的工作量加起來做得完嗎？人力不夠時刪減順序寫了嗎？
- **風險**：對照失敗歸因過了一遍嗎？關鍵假設有驗證方式嗎？合規紅線過了嗎？與客戶約束衝突嗎？
- **表達**：有沒有「做私域」「加強內容」這類沒動作的廢話？結論前置了嗎？

## 七點五、語言紀律（公開倉庫必讀）

- **交付物一律簡體中文**（客戶看的）—— 這是硬要求，`build_docx.py` 出稿前會檢查。
- **skill 內部文檔一律繁體**（維護者看的）：SKILL／AGENTS／README／`references/00–08`／`cases/`。
  （**`references/09–13`**「完整策劃標準／文案樣本庫／防返工協議／範式庫／頂級機構對標標準」以**簡體**維護 —— 它們的內容會**原樣進入簡體交付物**，用簡體維護可避免轉換走樣。）
- **唯一例外**：`references/范例/` 裡的**交付稿樣張是簡體**——因為它們就是交付物本身。

## 八、兩條使用紀律

1. **數據三級標註**：【已核實】／【行業認知】／【未核實】。**【未核實】不能寫進給客戶的交付物。**
2. **門禁不是形式** —— 你答得越細，方案越能用。含糊其辭只會得到一份正確但沒用的方案。
