# marketing-playbook · 使用说明

> 一句话：**你把客户情况说清楚，它给你一份完整的营销方案 Word 文档。**
> 不是查资料，是生成方案。

---

## 零、开新会话第一步（**别通读，先跑这条命令**）

```bash
python scripts/start_here.py --client "客户情况一句话"   # 人／主会话用
```

**它为什么存在**：仓库已经 263 万字，而**每次开新会话，执行 AI 都会想从头读一遍** ——
那是最大的浪费。这条命令把「要读的」压到 3 份以内、并明确列出**不要读什么**：

```
【① 必读】SKILL.md（只读 §0 门禁 / §二路由表 / §六自检清单）＋ 12-范式库.md（只读本单那一档）
【② 客户状况命中的打法方向】→ 去 00-打法库.md 按 §编号查，不通读
【③ 最相关的行业案例档】→ 只读「案例清单」那一段
【④ 明确不要通读】03 手册（13 万字）／00 打法库（116 条）／另外 51 个非本行业案例档
【⑤ 想查词就用检索】python scripts/start_here.py --grep "场景化"
```

> **核心思路：用「查」代替「读」。** 这比整理目录更省 —— 目录只让人找得到，检索让 AI 读得少。

## 一、用它之前要知道的一件事

**它会先问你一堆问题，问完才动手。**

这是刻意设计的。没搞清楚客户情况就出方案，等于算命。所以第一次使用时：

1. 它会对照 **13 项门禁清单** 逐项核对，列出你还缺哪些信息
2. 一次性把缺的问完（不会挤牙膏）
3. **产出《任务规则表》请你确认**（门禁答案＋交付结构＋红线）
4. **你确认之前，它不会出任何方案内容**

13 项门禁：卖什么／卖给谁／现在规模／卡在哪／预算／现有资源／时间死线／硬约束／决策人／竞争对手／过去试过什么／怎么算成功／**目标字数**。

> **为什么有「目标字数」这一项**：比赛提交、招标文件、客户模板常有字数或页数上限。先问再写，比写完再砍划算。

## 一点五、最高优先级条款（P0）＋ 八条强制协议（违反任何一条＝这次使用失败）

> ⛔ **P0 · 优先于下面八条，也优先于 skill 的一切默认结构。** 由一次真实返工经验反推（详见 `references/11-防返工交付协议.md`）。
> 完整版见 `references/11-防返工交付协议.md`（6 条铁律 ＋ 交付前自检 8 项 ＋ 4 条结构性根因）。

| P0 | 条款 | 白话解释 |
|---|---|---|
| **P0-1** | **你给的结构 > skill 的一切默认** | 你（或主办方）给了模板／大纲／目录／提交清单时，**它的优先级高于 skill 的默认八篇结构**。一级二级标题**逐字沿用**：不改写、不合并、不拆分、不重排、不自造；模板没有的内容**新增章节**补进去，而不是改造原标题 |
| **P0-2** | **你的素材要「看得见地插进去」** | 你给的大纲必须作为**文档中可见章节**出现，保留原名与编号（如「一、活动背景」）；⛔ 不许打散揉进别的小节——**那等于你的大纲消失了** |
| **P0-3** | **「skill 自检通过」≠「交付达成」** | skill 的自检只查它自己 care 的项，**不查「有没有用你给的模板标题」**。你的验收项（格式／字数／匿名／双格式／附件）必须**另行逐条核对并输出**——不许拿「自检全绿」当「可以交了」 |
| **P0-4** | **形状类任务先交 1 页目录** | 涉及结构／粒度／组织方式时，**第一版只交一页目录**，你确认后才写正文；一句话含两个约束 → 动手前**分别复述** |

> **一句话根因**：所有返工都源于「先默认生成全文当第一版」，而不是「**先锁形状**」。

| # | 协议 | 白话解释 |
|---|---|---|
| 1 | **启动即立规** | 问完就出一张《任务规则表》给你确认；**你之后每次纠偏＝规则表升级**，它要先复述再动手，不许当一次性修补 |
| 2 | **结构冲突「合并，不取舍」** | 你若有指定格式（比赛清单、客户模板），它会把该写的内容**映射进去，硬要素一件不丢**；不许为了贴合格式砍深度 |
| 3 | **交付前自检单原样输出** | 说「完成」之前，必须在回复里逐项打出 12 项自检单并标 ✅/❌；有 ❌ 就不许说完成 |
| 4 | **工具盘点先于路径** | 要读外部资料时，**先盘点已连接的连接器／API**，能用连接器就不许用爬虫硬绕（烧额度主因）；付费生成先报价 |
| 5 | **交付形态红线** | 对外一律**简体 `.docx`**；**内部过程文档（事实底稿／Agent 分工／裁决记录）不得混进交付稿** —— 你要的是作品，不是工作过程 |
| 6 | **每轮开头输出《流程状态》行** | 它每轮回复第一行必须是：`【营销方案 · 流程状态】门禁 13 项：x/13（缺：…）｜ 任务规则表：…｜ 当前阶段：…`。**缺了这一行，就代表它跑偏了** |
| 7 | **跨平台一致** | 不许依赖某个平台的特有能力；能力不足要降级（例如不能派多 Agent 就顺序扮演），**但降级不等于跳步** |
| 8 | **卡死处理（不许把自己卡死）** | 同一项校验**连续 2 次不过 → 停止重试**，把问题摊给你、给你 2–3 个选项选；脚本报错或环境不可用 → **降级成 Markdown 继续产出**；跳过一律**留痕**（明说哪几项没检查）。**不许**同一错误重试超过 2 次、不许因校验不过就不交付、不许静默跳过 |

> 这八条不是口号：执行 AI 最常见的五个失败模式（骨架式使用／跳过自检／门禁漏项／工具惯性绕路／结构冲突做减法）都在 `references/04-失败归因总库.md` 附录，每条协议各自堵住一个。

## 一点七、怎么一眼看出它有没有照做（你只需看 3 处）

| 看哪里 | 正常 | 有问题 → 你怎么说 |
|---|---|---|
| **回复第一行** | 有 `【营销方案 · 流程状态】…` | 没有这行 → 「**你没输出流程状态**」（它必须补上并回到正确阶段） |
| **动笔之前** | 先问你问题（门禁 13 项）→ 出《任务规则表》等你确认 | 直接开始写方案 → 「**先出任务规则表**」（强制走协议 1） |
| **说交付之前** | 原样输出 12 项自检单并标 ✅/❌ | 只说「已完成」→ 「**把 12 项自检单打出来**」（强制走协议 3） |

**这三句话就是你的保险**（记住就够，不必每次说）：

1. 「你没输出流程状态」
2. 「先出任务规则表」
3. 「把 12 项自检单打出来」

> 正常情况下协议会自动生效，这三句是兜底。但 AI 是几率性的 —— **你手上有这三句，它就没有跑偏的空间。**

**想要更硬的话**（可选）：在支持 hook 的平台（WorkBuddy／Claude Code）可以加装一个 Stop 钩子，AI 想结束回答时自动检查自检单，没输出就拦住。配置方法见 `AGENTS.md` §九 —— **但这是选配，不影响跨平台使用。**

## 一点八、卡死了怎么办（重要）

**校验是为了让交付更好，不是为了让交付不出来。** 如果它卡住不动了，按症状处理：

| 症状 | 你怎么说 |
|---|---|
| 反复改同一处、来回好几轮 | 「**卡在哪了？把错误原文贴出来**」→ 它必须把问题摊开，并给你 2–3 个选项选 |
| 跑脚本报错、环境不对（没装套件等） | 「**降级：不用脚本，直接出 Markdown**」→ 它应该继续产出，并注明哪部分未经校验 |
| 校验过不了但你不想再等 | 「**跳过这项，先出稿**」→ 允许用紧急出口出稿，但**必须标明哪几项没过校验** |
| 完全没反应（对话太长／工具超时） | 开个新对话，说「继续上一个营销方案，上次停在 X」 |

**它的三条红线**（你可以据此要求它）：

1. 同一个错误**不许重试超过 2 次**
2. **不许因为校验不过就不交付**（卡住必须上报，不能自己死磕）
3. **不许静默跳过校验**（跳过必须告诉你跳了哪几项）

> 一句话：**卡住就让它上报，别让它自己死磕。**

> 想跳过？只有明说「先按假设出一版」才行 —— 这时文档首页会标注「本方案基于未经验证的假设」并列出假设清单。

## 三、它会交付什么

交付稿的实际章节结构（**本区块由 `scripts/build_paradigm.py --doc-map` 生成，改骨架后重跑即可，不要手改**）：

| 章节 | 说明 |
|---|---|
| 执行摘要 | 五句话把全案说清：目标、主线、打法、预期、盈亏线。读完这五句就能决定要不要往下看。 |
| 核心结论卡片 | 决策者只看这一张就够：一张表讲完全案的关键数字。放在执行摘要正下方。 |
| 一 · 现状分析 | 先定问题类型，再写生意目标；后面四节全部是「凭什么这么判断」。 |
| 1.1 问题类型与目标 | 判断卡在哪一类，再把它翻译成一个可核验的生意目标。 |
| 1.2 真正的卡点 | 用「不是 X —— 是 Y」写一句：前半句否掉一个似是而非的解释，后半句指向一个能动手的环节。 |
| 1.3 已排除的假设 | 列出被数据或事实否掉的 2–3 个假设，证明你不是拍脑袋。 |
| 1.4 竞争与关联品牌扫描 | 头号对手按业务环节全链条拆，其余逐个一句，最后收一句差异点。 |
| 1.5 约束与风险底线 | 预算、时间、人力、合规四类硬约束各写一条，并写清「因此不做什么」。 |
| 1.6 市场盘子 | **自上而下答「盘子多大」，自下而上答「你够得着多少」。** 只给一个数无法验证量级。 |
| 〇 · 议题树与假设台账 | 先证明没漏掉一整块，再谈怎么打。BCG 判据：没有议题树就写正文＝不合格。 |
| 0.1 MECE分解 | 把营收拆成四个因子，用数据定位漏钱最多的一层。 |
| 0.2 假设台账 | 把方案成立所依赖的假设摆到台面上，并给每一条配上验证方式。 |
| 二 · 策略 | 全案最重的一章：先给打法组合，再给可抄案例。 |
| 2.0 打法组合 | 每条打法写清「具体动作 ＋ 四要素 ＋ 验收 ＋ 为什么」，多段文字，不要压成一张宽表。 |
| 2.0.1 可抄案例 | 每条打法配「1 张指名对标 ＋ 1 张本行业可抄」，再写我们怎么用。 |

| 2.0.7 概念测试 | **问谁、问什么、什么算过** —— 三要素缺一不可。只写「做了共鸣测试」不算做过测试。 |
| 2.1 三次收窄 | 时间、人群、动作各收窄一次 —— 预算有限时，窄才打得穿。 |
| 2.2 货盘与机制 | 卖什么组合、用什么机制把人留下来。 |
| 2.3 被低估的资产 | 客户手里**已经有了、却没被用起来**的东西。最省钱的增长往往不是再做一个活动，而是把已有资产摆到台前。 |

## 四、它内部怎么工作（六步）

```
第 0 步 门禁 ──── 13 项问清，没问清不出方案
第 1 步 事实底稿 ── 把客户告知的一切整理成唯一输入源
第 2 步 现状分析 ── 体检（数据事实 + 我的判断 + 已排除的假设）
第 3 步 多 Agent 分工 ── 策略 / 品牌 / 触达 / 文案 / 财务风控，各写各的
第 4 步 主理人裁决 ── 冲突裁决 + 合并成稿 + 跑自检
第 5 步 交付 Word ── 生成 .docx
```

**多 Agent 分工（每次都走）**：
各 Agent **只读事实底稿、不互读草稿**（避免互相迁就、越写越像）；冲突由主理人裁决并记录理由。

> ⚙️ **脚本链（真正的强制层）**：`python scripts/flow.py` 看流程状态 → **`composer.py` 把打法／模型／学者／案例
> 机械注入骨架**（知识绕不过）→ 模型只填空 → `selfcheck.py`（不过关不出稿）→ `run_pipeline.py`（唯一出口）。
> 逐步操作手册见 `references/08-操作流程SOP.md`。

## 七点五、语言纪律（公开仓库必读）

- **全仓库统一简体中文** —— 知识库、脚本注释、案例卡、文档、交付物，全都是简体。
- **交付物必须简体**（客户看的）—— 这是硬门槛，`selfcheck` 会**判硬错误**、
  `build_docx.py` 出稿前还会再喊一次。统一语言后这条没有放松，反而更该守：
  它现在的意义是**挡住外部粘贴进来的繁体**。
- **为什么取消双轨**（2026-09-18 定）：原先「交付物简体／内部文档繁体」的代价是
  一个永久的转换步骤（`composer` 注入知识库内容时要逐字转），而且「哪一份该是哪一种」
  只能靠人记 —— 记错就是交付稿混进繁体。统一之后：知识库是简体 → 注入时不用转，
  **少一个会出错的环节**，规则也从两条变一条。

⚠️ **两个地方必须保留繁体，别去「顺手统一」**：
1. `scripts/t2s_data.py` 的 `T2S_PAIRS` —— 繁体字表本身就是「**哪些字是繁体**」的判据，
   是 `selfcheck`【9】和 `build_docx` 侦测繁体交付稿的依据。转掉＝检测失效。
2. `scripts/smoke_test.py` 里的**繁体负向夹具** —— 它必须保持繁体，
   否则「繁体稿应被拦」这条测试就变成在测一份简体稿（永远该通过）→ **测试静默失效**。
   该行行尾带 `# lang-keep-trad`，`scripts/lang_unify.py` 会跳过它。

**维护工具**：`python scripts/lang_unify.py`（报还有什么繁体）／`--fix`（就地转）／`--strict`（当门槛）。
